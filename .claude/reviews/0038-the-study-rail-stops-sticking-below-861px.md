## Review 38 — 2026-09-11 · commit 10bdd5e: the study rail stops sticking below 861px

**One sentence:** *"Every single number in this change reproduced on my own browser — the rail really did ride 3516px down Pour at 390px and print over four blocks of text at y=1600, it is gone at every phone and tablet width now, and desktop is identical to the pixel before and after — so this was right to ship; the one thing I would still change is the breakpoint spelling, which leaves a hairline between 860 and 861px where the rail quietly stops sticking."* **PUSH** — and note this is an audit after the fact: PR #9 was merged at 19:06Z and 86766af has been live on hycudesign.com since. - **The diagnosis reproduced to the pixel, on my own browser, with my own script.** I served the pre-change stylesheet to a 390px viewport on `/work/pour/` and sampled every 100px of the page. One sticky element. The rail travels **3516px** down the document, and it sits on top of article text at **45 of the 53** positions I sampled. At exactly y=1600 I get **four** overlaps — `p 328x88`, **`p 328x223`**, `p 328x28`, `h2 328x80`. Same count, same worst measurement, same scroll position as the commit message claims. With the fix in place the rail computes `position: static` and the page has no sticky element at all. That is text printed over text on every one of the eight study pages, which is what Wyatt was looking at.
- **It was never only phones. Tablets were just as broken — at a width the test suite already visits.** At 820px (the tablet viewport `shoot.mjs` has used since Review 4) the old rail travelled **2029px** and covered text at **30 of 35** sampled positions, worst overlap 689x251px. So the site was wrong at every width from 860px down, for as long as the rule has existed, and the browser pass looked straight at 820px the whole time without a check that could see it. The commit says this; I confirmed it.
- **Desktop is untouched, measured rather than asserted.** At 1440px, before and after, the numbers are identical: sticky, **1703px** of travel, **zero** overlaps across 36 sampled positions, document height 3554px both, grid columns `616.016px 264.016px` both. "Desktop unchanged" is literally true here, not approximately. The rail still does the job it exists to do.
- **"The rail is the only sticky element on the site" is true by construction, not only by measurement.** `position: sticky` appears exactly once in `style.css`, and `study-rail` appears in exactly eight HTML files — the eight studies. I then counted sticky elements in a browser on all **thirteen** pages (the twelve the test visits, plus `404.html`) at 320, 390, 430 and 820px: zero everywhere, with no horizontal overflow on any page at any of those widths.
- **The 861px boundary is right, but it leaves a hairline.** One column at `max-width: 860px`, sticky at `min-width: 861px`. A window that lands between them — 860.5px, which browser zoom and some devices really do produce — matches neither, so you get the two-column layout with a rail that does not stick. That is cosmetic; it is not the fault leaking back, because the fault needs the one-column layout. Not a blocker. The conventional spelling is `min-width: 860.02px`, and I would make that change next time this file is open. At the integer boundaries I measured: 860px → static, one column; 861px → sticky, two columns, 2226px of travel, zero overlaps in 38 samples. Clean switchover.
- **Nothing wanted the rail sticky below 861px.** No JavaScript references `.study-rail` or `.rail` (`js/site.js`, `js/scene.js`); `check.mjs` only reads the rail's Capabilities row out of the HTML; no other CSS rule depends on the rail's `position`. Removing it below the breakpoint costs nothing.
- **The new check is sound for this fault, and it does not disturb the checks after it.** It returns before touching the scroll position on any page with no sticky element — so the home page, the only page carrying the headline, axis-label and graph-tile checks, is never scrolled at all. On the study pages it scrolls with `behavior: 'instant'` *and* an inline `scroll-behavior: auto` (both are needed: `html { scroll-behavior: smooth }` would otherwise animate the jump and the sample would measure a frame nobody sees), returns to y=0, and restores the inline style. The only check that follows it on those pages is the gutter check, which reads left edges and does not care where the page is scrolled to. No interference in the code, and none in the run.
- **Two soft spots in the check, neither blocking.** (a) It samples at most eleven positions per page (`step = max(200, height/10)`). This fault was present at 45 of my 53 finer samples, so it was never going to slip through — but a fault confined to a narrower band could. (b) It reads `p, h1, h2, h3, li` only; the eight study pages contain no `figcaption`, `h4`, `blockquote` or `dd`, so today it sees all of their text, but that is a fact about today's markup rather than a guarantee. And one thing the comment does not say: **the check is a policy, not just a fault test** — "no sticky element may ever overlap text." A sticky section header or a sticky table head, where text passing behind is the design, would fail it. Harmless while the site has one sticky element; worth knowing before anyone adds a second.
- **`sticky-overlap checks: 36` counts pages visited, not comparisons made.** On 24 of those 36 there is no sticky element and the function returns before comparing anything. `ran.gutter` is counted the same way, so this is house style rather than a new sin — but the number in the report reads larger than the coverage is.
- **`404.html` is not in the browser pass.** The `style.css` comment names 404 among the five pages that were fine, and it is — I opened it and counted zero sticky elements at four widths. But `shoot.mjs`'s page list has never included it, so the suite does not prove that sentence. Pre-existing, not this change's doing.
